- [Introduction to Authentication](https://developer.dealerware.com/docs/api-integration-process.md): To access Dealerware's API, you'll need to securely authenticate your requests. This process starts by obtaining your Client ID and Client Secret, which serve as your unique credentials. These keys are critical for API access, so ensure they are stored securely and never shared in public repositories or client-side code.  Dealerware's authentication process relies on generating an Access Token through our trusted authentication server. All interactions with our API require a valid token, ensuring secure, authorized access to resources. Always use HTTPS for all API calls to maintain data security and integrity.  This guide will walk you through each step of the authentication process, from requesting API credentials to securely making authenticated requests. - [Returns reporting data for a logical table search](https://developer.dealerware.com/reference/postreportingdata.md): This endpoint executes a report query against a logical table.  The server builds the query for the client from: - `columns`: the exact column labels to include - `filters`: equality filters using `{ column_name, value }` - `runtime_filters`: advanced runtime filters - `runtime_param_override`: parameter overrides  Access scope: - Before querying data, the server resolves `name_patterns` to exactly one logical table available   to the `custom_reporting` user group.  Behavior notes: 1. `/reporting/data.filters` is the simple query-string path and is currently equality-only. 2. `runtime_filters` supports richer operators. Use metadata to determine which operators are valid    for a given field. 3. DATE and DATE_TIME columns may include a date bucket suffix in `columns` and `filters` using    `Column Name.bucket` syntax. The server sends these to ThoughtSpot as `[Column Name].bucket`.    Supported buckets are `detailed`, `hourly`, `daily`, `weekly`, `monthly`, `quarterly`, and `yearly`. 4. ISO 8601 timestamp strings in `runtime_filters` are converted to epoch seconds before the request    is sent only when they include a time component. 5. `runtime_param_override` forwards parameter overrides as numbered `param1`, `paramVal1`, etc. 6. Single-OEM admins may omit `runtime_param_override.oem`; the server infers it from the    authenticated user. 7. OEM admins with access to multiple OEMs must send a non-blank `runtime_param_override`    entry with `name: "oem"`. 8. Non-OEM admins do not get OEM scoping from `runtime_param_override.oem`; any client-supplied    `oem` override is stripped and the server injects a runtime filter equivalent to    `preferred_dealer = true`. 9. The query filter `[filter_oem]=true` is added only when the effective outgoing    `runtime_param_override` includes `oem`. 10. The reporting response is returned with date-like values normalized for API clients.  Validation rules: 1. `name_patterns` must include at least one non-blank pattern. 2. `name_patterns` must resolve to exactly one authorized logical table. 3. At least one column is required. 4. Every filter column must also appear in `columns`. 5. `filters` is equality-only. 6. `runtime_filters` supports richer operators. 7. Multi-OEM admins must provide `runtime_param_override.oem`. 8. Dotted column names must use one of the supported date bucket suffixes.  Pagination: - `page` (1-based) and `per_page` control how many rows are returned in a single response. - Total-record counts are not surfaced because they are known to be inaccurate.  Typical flow: 1. Call `/reporting/metadata`. 2. Copy `data_sources[*].name_patterns`. 3. Choose one or more values from `data_sources[*].column_names`. 4. Optionally apply equality filters using `data_sources[*].filters`. 5. Optionally add `runtime_filters` using `data_sources[*].runtime_filters`, for example date ranges    with `BW_INC`. 6. Optionally add `runtime_param_override` using `data_sources[*].runtime_parameters`.    Include `oem` only when the authenticated user has access to multiple OEMs.    Single-OEM admins may omit `oem`, and non-OEM admins should not rely on sending it. 7. Call `/reporting/data`.  Example query generation: - Request:   `columns: ["OEM", "Region"]`   `filters: [{ "column_name": "Region", "value": "West" }]` - Generated query string:   `[OEM] [Region] [Region]="West"` - Date bucket request:   `columns: ["Actual Pickup At.daily"]` - Generated date bucket token:   `[Actual Pickup At].daily`
- [Returns reporting metadata for logical tables](https://developer.dealerware.com/reference/postreportingmetadata.md): This endpoint is the discovery step for reporting.  It searches logical tables and returns a reduced response built for API clients: - `name_patterns`: the stable selector to send to `/reporting/data` - `column_names`: the exact column labels clients may request in `/reporting/data.columns` - `filters`: query-string filter metadata for `/reporting/data.filters` - `runtime_filters`: column-level runtime filter metadata for `/reporting/data.runtime_filters` - `runtime_parameters`: parameter metadata for `/reporting/data.runtime_param_override`  The response intentionally strips out the large raw metadata detail payload. Results are limited to logical tables available to the `custom_reporting` user group.  Typical flow: 1. Call `/reporting/metadata` with optional `name_patterns` that match the worksheet or logical table. 2. Read `data_sources[*].column_names` and let the user choose which columns to include. 3. Read `data_sources[*].filters[*]` to build `/reporting/data.filters`. 4. Read `data_sources[*].runtime_filters[*]` to build `/reporting/data.runtime_filters`. 5. Read `data_sources[*].runtime_parameters[*]` to build `/reporting/data.runtime_param_override`. 6. Call `/reporting/data` with `name_patterns`, `columns`, and whichever of those three inputs you need.  Behavior notes: 1. `column_names` comes from `metadata_detail.columns[*].header.name`. 2. If only top-level `column_names` are available, the API still returns them but leaves    `filters` and `runtime_filters` empty because filterability cannot be inferred. 3. `filters[*].operators` only describes `/reporting/data.filters`, which is currently equality-only. 4. `runtime_filters[*].operators` describes `/reporting/data.runtime_filters`. 5. Date and datetime runtime filters expose range operators such as `BW` and `BW_INC`. 6. `runtime_parameters` is sourced from useful raw parameter metadata when present. 7. Date-like metadata values are returned as ISO 8601 strings. DATE values use `YYYY-MM-DD`;    DATE_TIME values use UTC timestamps such as `2026-04-01T00:00:00Z`.  Pagination: - `page` (1-based) and `per_page` control how many logical tables are returned in a single response. - Total-record counts are not surfaced because they are known to be inaccurate.  Access scope: - `name_patterns` defaults to `["%"]` when omitted. - Results are permission-scoped to the `custom_reporting` user group.
